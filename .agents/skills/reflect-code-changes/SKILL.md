# 复查代码改动

把已经完成的代码修改整理成尽可能小、清晰、有效且易维护的差异。只检查当前任务的改动，并保留工作区中与任务无关的修改。

## 工作流程

1. 根据用户请求和代码差异还原修改意图，列出属于当前任务的文件，不得擅自扩大范围。
2. 如果存在 `.codegraph/`，先用 CodeGraph 追踪改动符号、调用方、被调用方和可复用的项目模式，再用 `rg` 补充缺失信息或精确文本检查。
3. 检查复用性：
   - 接受新代码前，先查找现有的服务、辅助函数、类型、组件、夹具或扩展点。
   - 语义一致时优先复用；不要为仅使用一次的逻辑强行抽象。
   - 只有存在当前的第二个使用方，或符合项目既有扩展模式时，才认为新增抽象合理。
   - 给出“已复用”“新增代码合理”或“发现重复”的明确结论，不得虚构按代码行计算的复用率。
4. 检查有效性：
   - 追踪“用户请求 → 入口 → 修改后的行为 → 可观察证据”。
   - 确认测试验证的是行为，而不是简单复述实现细节。
   - 在安全的前提下，删除死分支、重复状态、未使用导入、过时回退和临时诊断代码。
5. 检查人类可理解性：
   - 让命名表达意图，并使控制流在局部即可理解。
   - 删除不能澄清边界的透传包装和预设性间接层。
   - 注释应解释约束或原因，而不是复述语法。公共边界应遵循仓库类型规范。
   - 与压缩但晦涩的写法相比，优先选择稍长但直观的实现。
6. 直接整理明确、低风险且属于当前范围的问题。不得仅为风格重构无关代码或改变行为；遇到重要取舍时应明确报告，不得猜测。
7. 对整理后的差异再检查一次。本轮整理产生的修改属于同一次调用，不得递归触发本技能。
8. 按仓库 `AGENTS.md` 完成最终验证。如果验证又引发代码修改，再次使用本技能。

## 完成条件

只有满足以下条件才能结束：

- 没有已知的项目抽象被无谓重复；
- 请求的行为已有证据支撑，或者明确说明缺少哪些证据；
- 维护者不查看对话记录也能理解改动后的代码；
- 当前任务的差异中没有无关产物。

最终用“复用性”“有效性”“可理解性”“验证”四行简要报告，只说明具体决策和剩余风险。
