# 复查代码改动

对当前任务已经完成的代码修改进行一次收尾审查和整理，使最终差异尽可能小、清晰、正确、可维护。

只处理当前任务引入或修改的内容。工作区中与当前任务无关的修改必须原样保留，不得顺手整理。

## 核心原则

按以下优先级判断是否需要修改：

1. 正确性
2. 当前任务范围
3. 复用已有实现
4. 删除当前任务产生的冗余
5. 可理解性
6. 差异最小化

如果某项修改只改善风格，却不改善正确性、复用性、理解成本或维护成本，则不要修改。

不为“可能以后会用”提前增加抽象。

---

## 1. 确定当前任务范围

先根据以下信息还原修改意图：

* 用户当前请求；
* 当前代码差异；
* 当前分支已有上下文；
* 与改动直接相关的测试。

列出属于当前任务的文件和主要修改符号。

不得因为发现邻近问题而扩大范围。

如果无法可靠判断某个已有修改是否属于当前任务：

* 保留该修改；
* 不主动整理；
* 在最终报告中说明无法确认归属。

---

## 2. 读取仓库约束

优先查找并遵守当前目录及父目录生效的：

* `AGENTS.md`
* 仓库开发规范
* 测试规范
* lint / format / type-check 配置

只应用与当前修改范围相关的规则。

---

## 3. 分析改动影响

如果仓库存在 `.codegraph/` 且 CodeGraph 可用：

优先使用 CodeGraph 检查当前改动符号的：

* 定义位置；
* 调用方；
* 被调用方；
* 继承或实现关系；
* 已有同类实现；
* 项目现有扩展模式。

随后使用 `rg` 做精确文本搜索和补充验证。

如果 CodeGraph 不存在、不可用或信息不足，直接使用 `rg` 和代码阅读完成分析，不因工具缺失阻塞任务。

搜索范围围绕当前任务涉及的符号和行为，不进行无目的全仓扫描。

---

## 4. 检查复用性

接受新增代码前，搜索项目中是否已经存在语义一致的：

* service；
* helper / utility；
* 类型；
* 组件；
* fixture；
* adapter；
* extension point；
* 测试辅助能力。

判断规则：

### 已复用

已有能力可以直接满足需求，当前改动已经正确使用。

### 新增代码合理

满足任一条件即可：

* 项目中不存在语义一致实现；
* 当前逻辑仅有一个使用方，局部实现更加直接；
* 新抽象符合仓库已有扩展模式；
* 已存在第二个真实使用方需要共享。

### 发现重复

已有实现可以满足当前需求，但当前修改重新实现了相同语义。

发现明确重复且替换风险低时，直接改为复用已有实现。

不要：

* 为单一调用点强行提取 helper；
* 为假设中的未来需求建立接口；
* 为减少几行重复代码增加新的间接层；
* 虚构“复用率”等无可靠依据的指标。

---

## 5. 检查有效性

建立最短行为链：

`用户请求 → 代码入口 → 修改逻辑 → 外部可观察行为 → 验证证据`

逐项确认：

* 修改确实覆盖用户请求；
* 修改后的分支能够从真实入口到达；
* 返回值、状态变化、副作用或错误行为符合预期；
* 新增配置或参数确实被消费；
* 错误处理不会吞掉需要暴露的问题；
* 测试验证最终行为，而非单纯复制实现逻辑。

重点检查当前任务新增的：

* 永远无法进入的分支；
* 重复条件；
* 重复状态；
* 未使用变量或导入；
* 无效 fallback；
* 临时日志；
* debug 开关；
* 临时兼容代码；
* 已失效注释；
* 测试中的无意义 mock 或断言。

明确属于当前任务且可以安全删除时，直接删除。

如果缺少足够证据证明行为正确，不猜测，在最终报告中指出缺失的验证。

---

## 6. 检查可理解性

代码应允许维护者仅阅读当前文件和必要依赖即可理解主要控制流。

检查：

* 命名是否表达业务意图；
* 条件判断是否容易理解；
* 数据转换是否有明确边界；
* 错误路径是否清晰；
* 是否存在无意义透传包装；
* 是否引入仅用于转发调用的间接层；
* 注释是否解释约束、原因或非显然行为；
* 公共接口是否符合仓库类型和命名规范。

优先保留直观代码。

不要为了减少代码行数使用晦涩表达。

不要仅为个人代码风格修改已有代码。

---

## 7. 整理当前差异

仅修改满足以下条件的问题：

* 明确属于当前任务；
* 判断依据充分；
* 修改风险低；
* 不改变请求之外的行为。

整理后重新检查当前 diff，确认：

* 没有误改无关文件；
* 没有新增无关格式化差异；
* 没有意外扩大 API；
* 没有留下临时产物；
* 当前任务差异已经达到完成目标。

本步骤产生的修改属于本次复查的一部分，不再次递归执行本 Skill。

---

## 8. 验证

按照当前仓库 `AGENTS.md` 和项目规范执行与修改范围匹配的最小充分验证。

验证优先级：

1. 当前修改对应的目标测试；
2. 相关模块测试；
3. type check / compile；
4. lint / format；
5. 仓库明确要求的其他检查。

避免在没有必要时运行与当前任务无关的大范围测试。

如果验证失败：

* 当前修改导致的问题：修复后重新执行相关验证；
* 与当前任务无关的已有失败：不要修改无关代码，在最终报告中说明；
* 无法执行验证：说明原因以及缺失的证据。

如果修复验证失败需要再次修改代码，只重新检查受该修复影响的差异，不重新扫描整个任务。

---

## 完成条件

同时满足以下条件才能结束：

* 当前任务范围已经明确；
* 没有已知项目能力被无谓重复；
* 没有明显死代码、临时代码或无效状态；
* 用户请求对应的行为链成立；
* 行为存在验证证据，或明确记录缺失证据；
* 代码无需依赖对话上下文即可理解；
* 当前 diff 中没有本任务产生的无关修改；
* 工作区原有无关修改未被破坏。

---

## 最终输出

仅输出四行：

**复用性**：说明复用了什么、为何新增代码合理，或具体指出仍存在的重复。

**有效性**：说明用户请求对应的行为是否成立，以及关键证据或剩余缺口。

**可理解性**：说明实际做过的简化、命名或控制流调整；无调整则说明无需调整。

**验证**：列出实际执行并通过的验证；失败或未执行时明确说明原因和剩余风险。
