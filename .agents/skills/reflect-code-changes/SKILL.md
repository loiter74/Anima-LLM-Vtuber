# Simplify：简化当前成果

对当前任务已经形成的成果进行一次结构化简化。

目标是在保持目标、行为、约束和必要信息不变的前提下，删除不必要的复杂度，使最终成果更直接、更少冗余、更容易理解和维护。

适用于：

* 代码与测试；
* 配置与脚本；
* Prompt / Skill / Agent 指令；
* 文档与说明；
* API / 数据结构；
* 工作流与 SOP；
* 架构和模块设计；
* 方案、规则和其他结构化成果。

Simplify 不等同于格式化、润色、全面审查或提交前检查。

---

## 核心原则

按以下优先级执行：

1. 保持目标和必要行为正确；
2. 删除无价值复杂度；
3. 合并重复表达或重复机制；
4. 复用已有能力和已有概念；
5. 减少状态、层级、分支和例外；
6. 提升局部可理解性。

允许为了获得明显更简单的结构，对当前任务依赖的既有内容进行局部重构。

不以改动量最小为目标。

如果较大的局部调整能够显著降低最终复杂度，可以执行。

不要为了形式上的统一、个人偏好或理论上的优雅增加修改。

---

## 1. 确定真正目标

先回答：

* 当前成果要解决什么问题？
* 哪些行为、信息或约束必须保留？
* 哪些部分只是实现手段？
* 哪些历史结构正在增加当前成果的复杂度？

建立：

`目标 → 必要约束 → 当前结构 → 最终结果`

后续简化围绕这条路径进行。

如果某个元素删掉后不影响目标、行为、约束或理解，则优先考虑删除。

---

## 2. 确定简化范围

允许处理：

* 当前任务新增或修改的内容；
* 当前成果直接依赖的既有结构；
* 与当前实现发生重复的历史内容；
* 为当前路径增加复杂度的旧包装、状态、规则或层级。

如果重构某个既有结构能够直接降低当前成果复杂度，则属于范围。

不得因为发现其他问题扩展到无关区域。

---

## 3. 尽可能并行分析

如果环境支持子 Agent，应优先并行分析。

通常最多拆成 3 个方向：

### A. 重复与复用

寻找：

* 重复逻辑；
* 重复信息；
* 重复规则；
* 重复状态；
* 已有可复用能力；
* 相同概念的不同表达。

### B. 结构复杂度

寻找：

* 多余层级；
* 无意义包装；
* 过度拆分；
* 过度抽象；
* 重复分支；
* 例外堆叠；
* 不必要中间状态；
* 可以合并的步骤。

### C. 约束保护

确认：

* 哪些行为必须保持；
* 哪些信息不能丢失；
* 哪些外部调用或使用方受影响；
* 最小验证方式。

各 Agent 围绕同一目标工作，避免重复进行全面审查。

没有子 Agent 时，也应尽可能并行执行独立搜索、分析和验证。

---

## 4. 通用简化规则

### 删除

优先删除没有独立价值的：

* 死逻辑；
* 重复信息；
* 重复步骤；
* 未使用状态；
* 过期兼容；
* 临时结构；
* 无意义注释；
* 已被其他规则覆盖的规则；
* 没有实际使用方的扩展点。

---

### 合并

如果多个元素承担相同职责，考虑合并：

* 相似函数；
* 相似规则；
* 相同数据源；
* 重复状态；
* 重复条件；
* 重复说明；
* 重复验证步骤。

一个事实尽量只维护一个来源。

一个规则尽量只定义一次。

---

### 内联

如果一个中间层：

* 只有一个真实使用方；
* 只做转发；
* 没有独立业务语义；
* 不隔离重要边界；
* 删除后更容易理解；

优先内联。

适用于函数、类、模块、配置层、Prompt 小节、工作流节点等。

---

### 减少状态

检查是否存在：

`A → B → C`

但实际上 B 可以直接从 A 推导。

如果可以，则删除 B。

避免多个位置分别维护同一事实。

---

### 减少分支

如果多个路径最终产生相同结果，合并公共路径。

优先：

* 统一默认行为；
* 提前处理异常；
* 删除无意义特殊情况；
* 使用共同规则覆盖多个分支。

不要为了极少出现且没有明确需求的情况增加永久复杂度。

---

### 减少层级

检查是否存在：

`入口 → wrapper → adapter → helper → 实际逻辑`

其中部分层级没有提供：

* 边界隔离；
* 复用；
* 独立语义；
* 扩展价值。

删除没有实际作用的层级。

---

### 简化表达

对文档、Prompt、Skill 和规则：

删除：

* 重复要求；
* 已由更高层规则隐含覆盖的条目；
* 多次表达同一约束的近义句；
* 不影响执行结果的解释；
* 无法指导具体行动的抽象要求。

优先使用：

`条件 → 动作 → 停止条件`

而非大量描述性文字。

---

## 5. 判断抽象是否值得保留

抽象至少应提供一种明确价值：

* 多个真实使用方；
* 隔离复杂逻辑；
* 隔离外部边界；
* 形成稳定接口；
* 符合当前系统已有扩展模式；
* 显著减少重复；
* 明显降低认知负担。

如果抽象只是把简单内容拆到另一个地方，不保留。

不要为可能出现的未来需求提前增加结构。

---

## 6. 判断“简化”是否真的更简单

每次重构后检查：

* 元素数量是否减少？
* 状态数量是否减少？
* 概念数量是否减少？
* 跳转层级是否减少？
* 分支数量是否减少？
* 同一事实的来源是否减少？
* 理解主要路径需要查看的位置是否减少？

如果只是把复杂度从一个地方搬到另一个地方，不算简化。

如果代码行数减少但理解成本增加，也不算简化。

---

## 7. 直接执行低风险简化

对于结论明确且能保持必要行为的改动，直接执行。

包括：

* 删除冗余；
* 合并重复；
* 内联包装；
* 合并状态；
* 简化流程；
* 调整局部职责；
* 重构当前路径上的历史结构。

如果需要大量额外假设才能确认安全，则保留现状。

不要为了找到更多优化而无限扩大分析范围。

---

## 8. 最小验证

验证重点只有两个：

1. 必须保留的行为或信息仍然存在；
2. 简化后结构确实减少了复杂度。

根据成果类型选择最低成本验证：

* 代码：相关测试、编译或类型检查；
* 配置：解析、加载或最小运行验证；
* Prompt / Skill：检查规则覆盖、冲突和执行路径；
* 文档：检查信息完整性和重复；
* 工作流：检查输入、关键步骤和输出；
* API / 数据结构：检查调用方和兼容边界。

独立验证尽可能并行。

不要默认执行与 Simplify 无关的全面检查。

---

## 9. 停止条件

满足以下条件立即停止：

* 没有明显重复；
* 没有无价值层级；
* 没有重复状态；
* 没有可安全删除的例外或包装；
* 主要路径已经可以局部理解；
* 继续修改只能改善风格；
* 进一步简化需要明显扩大任务范围。

追求足够简单，不追求理论最优。

---

## 最终输出

仅报告：

**删除**：删除了哪些无价值结构或信息。

**合并**：合并或复用了哪些重复能力。

**简化**：减少了哪些状态、层级、分支或步骤。

**验证**：如何确认目标和必要行为仍然成立。
